A. PER-PANE READER CONTROLS
==================================================

The current global "show/hide reader controls" button in the top-left navigation is no longer wanted.

Remove that global reader-control toggle from the top-left ribbon.

Instead, each reader / visualization pane must control its own reader toolbar independently.

For each pane header use this order:

    +    A/B    show/hide reader controls

So:
1. `+` first
2. pane identifier `A` or `B`
3. per-pane show/hide reader-controls button

Pane A and pane B must be independent.

Example:
- Pane A may have its PDF controls hidden
- Pane B may keep its PDF controls visible

Persist this as part of the pane/workspace reading state.

Do not make this a new global setting.

Also remove the `*` character currently used to indicate the selected pane.
The existing visual highlighting is enough.

--------------------------------------------------
SQL
--------------------------------------------------

SQL questions should train reasoning, not just syntax.

Preserve this canonical progression in the content model/documentation so later questions can follow it:

1. filter / aggregate
2. joins + cardinality
3. windows + ties
4. compose logic with CTEs
5. alternative techniques + deeper reasoning
6–8. onsite/deeper reasoning families

The user's canonical Q1–Q5 template is:

Q1 — WHERE + GROUP BY

Main:
"Classic SQL screener: filter to PAID orders in 2026 and return total net_amount per customer. What clauses do you need, and what is the output grain?"

Follow-up:
"How would you keep only customers whose total paid revenue exceeds 1000?"

Intent:
WHERE filters rows.
GROUP BY changes the output grain.
HAVING filters aggregated groups.

Q2 — JOIN + aggregation

Main:
"Classic SQL screener: return total paid revenue for every customer, including customers with no paid orders. Which join do you use and where should the paid-order filter go?"

Follow-up:
"What happens if one customer has multiple matching dimension rows before you SUM revenue?"

Intent:
LEFT JOIN preservation.
Predicate placement.
Join cardinality.
Fan-out / duplicated revenue.

Q3 — second-highest salary

Main:
"Classic SQL screener: how would you return the second-highest distinct salary, and how do ROW_NUMBER, RANK and DENSE_RANK differ?"

Follow-up:
"How would you return the second-highest distinct salary within each department?"

Intent:
ranking
ties
distinct rank
PARTITION BY

Q4 — CTE + composition

Main:
"Classic SQL screener: when a problem needs aggregation followed by ranking/filtering, why might you use a CTE, and is a CTE automatically faster than a subquery?"

Follow-up:
"Write a CTE that aggregates customer revenue, then ranks customers by revenue."

Intent:
decompose logic.
Do not teach that WITH is automatically faster.

Q5 — previous row

Main:
"Classic SQL screener: how can a self-join reproduce previous/next-row logic, when would you prefer LAG/LEAD, and how would you respond if the interviewer restricts available SQL features?"

Follow-up:
"Given daily account balances, return each balance and the previous observed balance using both LAG and a self-join."

Intent:
alternative techniques
deterministic ordering
row multiplication
feature restrictions
reasoning rather than memorized syntax

Also preserve these harder families for future expansion:

- Compositional SQL
- Temporal / relational logic
- Optimization reasoning

For this bounded prototype, minimum THREE visible SQL items are enough, but structure the data so the full Q1–Q5 sequence can be added without changing components.
