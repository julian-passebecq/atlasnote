# AtlasNote V2.3 immutable history archives, schema 1

## Release boundary
This finalization candidate is **BLOCKED**, with the same safe read-only implementation
as the exact 66f9387 baseline. Archive creation/verification, removal preview and exact
attachments remain available. No destructive IDB transaction is shipped; the public
method throws and the commit UI remains disabled even after trusted saved-file selection.
The new guard test is not rollback proof. All 13 fault cases and four actual capacity
recovery boundaries remain mandatory, explicitly blocked until real-browser evidence.
No unverified transaction proposal is promoted into production or included as a working
compactor. See `FINALIZATION.md` for the full all-five-store proof and exact build rule.

## Container and manifest
The format is `atlas-history-archive`, archiveSchema 1, in the existing bounded ZIP
transport. `archive.json` contains the descriptor, ancestor descriptors, revision shard
paths, review shard paths and SHA-256 table. Revision/review JSON shards target 2 MiB.
`assets/00000.<extension>` contains exact bytes, not URLs or guesses. The outer
`atlas-transfer.json` independently inventories file SHA-256 values. No nested ZIP,
executable source, ZIP64, symlink, traversal, case-colliding path or unlisted file is allowed.
Existing transport limits remain: 6,000 entries, 250 MiB expanded, 25 MiB per entry,
compression-ratio limit 500. Large data can be rejected safely; this is not an unlimited archive.

Descriptor: `kind:archive`, schemaVersion/archiveSchema 1, archiveId, rootHash,
createdAt, provenance, sourceEpoch, sourceHistoryHash, ranges, assets, reviews, counts.
Each range owns the oldest contiguous prefix of one exact resourceKey. Each thin
revision preserves every original field except snapshot: ID, stable resource/type,
number, parent, timestamp, hash, source/summary, restore/derive lineage and ChangeSet ID.
The full immutable row including snapshot is in a shard. IDs, hashes and numbering
are never rebased. Current heads cannot be externalized; retain defaults to two live
versions, with a minimum of one. Closed audit rows are eligible only when every
revision they own is in this same prefix selection. Pending/staged and spanning reviews
remain live. Review plans remain in the archive, not in the thin index.

A later range records the preceding archive ID, root, final revision ID and final number.
The index rejects duplicates, overlaps, gaps, mismatched previous owners and missing
live heads. It preserves 256-descriptor, 25,000-revision/archive and 64 MiB structured
archive limits. Thin metadata still occupies local capacity; unlimited free history is
not promised. An archive containing only closed audit rows is allowed.

## Root and exact identity
Stable JSON serialization is the repository's sorted-key `stable()` implementation.
The archive root is SHA-256 of the stable manifest with only descriptor.rootHash
omitted. File hashes bind all shard and asset bytes. The prepared ZIP also has a
whole-file SHA-256, separate from the logical root (ZIP timestamps can change).
Saved-file re-selection requires both exact root/descriptor and exact ZIP SHA-256.
Read-only attachment requires the exact persisted descriptor and all ancestor
descriptors, not merely a matching filename or a set of similar revisions.

All serialized output is re-opened and verified before download is offered. Verification
checks transport, manifest shape, file inventory, every payload hash, resource/canonical
Article-QCM identity, revision snapshot hash, sequence/lineage, audit associations,
PDF provenance, media safety, byte lengths and local dependency closure. Hashes prove
byte integrity relative to the expected descriptor; they are not publisher signatures,
encryption or proof that an external file will remain available forever.

## Saved-file ceremony and blocked deletion
Prepare -> self-verify -> download -> independently choose actual saved file -> verify
again -> show exact revision/review/asset deletion IDs and byte estimate. A native,
trusted file-input event and session-only WeakMap receipt guard the ceremony. The
receipt is single-use and never serialized or exported to the Agent. Synthetic events,
generated bytes alone, wrong files and altered bytes do not authorize anything.
In this candidate even an exact saved file DOES NOT enable deletion. The final
compaction button is permanently disabled and clearly says why.

The future transaction must re-read and compare all five stores, epoch, original
history hash and removal-set hash within one IndexedDB readwrite transaction before
writing the descriptor/removing rows. Every fault must leave exactly the same key/value
records, heads, projections, audit and asset bytes. No background pruning is allowed.
See QA_MATRIX.md for the unpassed concurrency/abort/quota matrix.

## Attachment and navigation
Attachments are verified, cloned, session-memory-only objects. They never modify
IndexedDB, current heads or pending review decisions. A missing exact archive produces
its ID and root requirement; current content is never substituted. Detach is immediate.
After reload re-select the archive(s), or the complete recovery bundle, to browse them.
Current resource snapshots and all still-live history remain usable without archives.
The archived reader, Compare and manual/reviewed restore reuse existing adapters.
